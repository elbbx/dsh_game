## 1. 为什么必须多对话框、多模块
单个超长Codex对话框容易忘记前期约束；多个对话框直接写同一套核心脚本又会发生冲突。因此使用一个**主架构集成对话框**保存全局契约、审核和合并结果，另开若干专用对话框，每个只负责一个模块。在开发过程中不要把整个106章原规划重复粘给每条会话；阅读对应模块规格与契约即可。

## 2. 建仓与备份（Windows PowerShell 示例）
**在你现有的Godot项目根目录执行，不会替你创建游戏工程。先备份现有工程。**
```powershell
cd 'D:\GameProjects\OvercastVeil'
git init
git add .
git commit -m 'baseline: existing Godot project'
git branch -M main
```
将本ZIP的 `00_开始这里`、`01_Codex多对话框流程`、`02_模块独立规格`、`03_游戏数据表`、`04_建筑可视化`、`05_Godot参考代码`、`06_对话框可复制提示词`、`07_验收与性能测试` 复制到`docs/design-kit/`，不要覆盖项目已有Godot脚本。将`09_资料与来源/AGENTS_可复制到项目根目录.md`按照现有项目情况审阅后再保存为项目根目录`AGENTS.md`。

## 3. 使用Codex的方法
任选Codex IDE扩展、CLI或桌面客户端。CLI需要先安装、打开工程目录并按官方指引登录，命令通常为`codex`。安装方式以官方文档为准，避免猜测系统版本。主对话框先用`06_对话框可复制提示词/主架构对话框.md`，核对现有工程、输入、场景和存档；不授权大改代码。

## 4. 一个模块一个Git工作树（推荐）
```powershell
# 在主项目目录运行，确保分支名不冲突
git worktree add ..\OvercastVeil-M00 -b feat/m00-core
git worktree add ..\OvercastVeil-M10 -b feat/m10-chunks
git worktree add ..\OvercastVeil-M04 -b feat/m04-inventory
```
在对应路径中分别打开独立Codex对话框，严格阅读各自提示词。不同worktree之间没有未提交修改共享；各自能安全提交。请先完成M00再并行后续模块，M10/M11需在M00接口确认后进行。**不要在未分离worktree的情况下把三个Codex窗口同时指向同一个脚本目录。**

## 5. 每个对话框必须进行的六步
1. **发现**：只读扫描，报告工程结构、依赖、可复用脚本和测试入口。
2. **计划**：列具体文件路径、公共接口、最小可运行切片、验收命令。等你确认或由已授权开发规则确认后实施。
3. **数据优先**：先准备Resource/JSON/CSV验证与幂等处理，不先做画面特效。
4. **最小演示**：制作单一测试关卡/Debug按钮，例如仅2×2区块、3只丧尸、一栋两层房屋。
5. **验证**：运行Godot脚本检查、功能测试、快照测试、性能计数、人工可视化测试，保存结果日志。
6. **交接**：提交小而清晰的commit，输出handoff文档，主对话框核对再合并。

## 6. 分支合并与回滚
```powershell
# 在主工程目录，且工作区干净
cd 'D:\GameProjects\OvercastVeil'
git status
git switch main
git merge --no-ff feat/m00-core
# 核对并运行真实项目测试后，才合并依赖分支
```
若在主分支发现一个底层接口错误，主对话框先修接口、更新契约、发布变更说明，其他分支再合入，避免多个Codex各自修复同一方法。不要用`git reset --hard`强行处理冲突，以免丢失未保存资产。

## 7. 推荐并行窗口组合
| 阶段 | 主窗口 | 同时允许工作的窗口 | 合并门禁 |
|---|---|---|---|
| P0 | 规则/接口 | M00（单独） | 唯一ID、时钟、事件契约测试 |
| P1 | 检查架构 | M23存档、M02角色状态 | 存档可还原实体/角色 |
| P2 | 性能集成 | M10区块、M06物品、M05HUD原型 | 初次2×2区块不卡顿 |
| P3 | 世界移动 | M11导航、M04背包、M01天气 | 路径跨区块、实时UI仍能跑 |
| P4 | 战斗 | M08生成、M07武器、M12建筑数据 | 稳定population ID和命中 |
| P5 | 可玩切片 | M09丧尸AI、M13家具、M03医疗 | 开门/搜刮/追逐/治疗全流程 |
| P6 | 产业闭环 | M14采矿、M15制造、M26农耕 | 资源→配方→设施成品 |
| P7 | 据点 | M16电网、M17 NPC、M21衣物 | 电量结算、NPC任务合法 |
| P8 | 远征 | M18车辆、M22地图布局、M24声源 | 开车跨区块、敌人受枪声影响 |
| P9 | 异常 | M19克苏鲁、M20裂隙 | 车辆与乘员原子转层 |
| P10 | 验收 | M25性能与回归（独占集成） | 30分钟循环测试与存档 |

同一模块一旦开始真实代码实施，应保持一个负责窗口；设计素材可以并行，但公共基础代码不要多人改写。

## 8. 初始垂直切片（不要先做全城）
建议首个可玩切片：2×2个64m区块，一条道路、一栋双卧平房、一栋便利店、一辆车、10—20只普通丧尸、1只T1观察者、少量药品食物、一个可保存的小据点。完成走路、疾跑、背包、远近战、声音引怪、门窗、拾取、搜刮、入室、撤退、存档后再扩张。

## 9. 为什么优先做底层而非美术
建筑、物品、车辆内容多不代表核心系统已经可玩；先确定ID、存档、区块导航和AI生命周期，随后将数据表逐步导入可以避免制作上千物品后重写所有脚本。

## 11. 常见失败修复
- **Godot导入错误**：先验证资源路径/类型，再查脚本；不要无差别重新生成模型。
- **导航卡门**：记录门Portal当前状态、Navmesh层、agent半径和重规划时间，不要把NPC直接传送进门。
- **重复物品/重复车辆**：查`entity_id`和事件WAL，不要只靠`queue_free()`掩盖根因。
- **流送卡顿**：剖析加载、主线程实例化与Navmesh烘焙分别占时；先限制每帧激活预算。
- **Codex忘记要求**：把决策写入`AGENTS.md`和`接口契约.md`，新任务先读必读文件。

## 12. 授权范围建议
在正式项目中执行文件删除、依赖升级、批量资产修改和存档迁移前，让Codex先列出影响范围。每次开发只授权一个小任务，不要同时要求“完成全地图、AI、建筑、所有武器”。
