# M00｜世界架构、统一契约与事件生命周期——独立可执行设计书

> **定位：**本文件先给本模块的完整可执行设计与对应数据，再附106章原规划中属于本模块的条款。表中数值为初始游戏平衡配置，非已测试结论。

## 1. 玩家体验与系统边界

稳定身份、世界位置、共享态、独立层状态、版本迁移；限制各模块所有权。本模块不得绕过物品所有权、世界层身份、世界时钟和全局事件幂等机制。

## 2. 完整业务处理链

1. **初始化创建游戏世界与seed**：输入由唯一对象ID、世界层、当前世界时钟以及必要的物品/技能/位置构成；先验证目标、条件和容量，再发布带event_id的动作事件；最后在统一状态记录中提交变更，更新显示并记录异常日志。
2. **生成entity_id和definition_id**：输入由唯一对象ID、世界层、当前世界时钟以及必要的物品/技能/位置构成；先验证目标、条件和容量，再发布带event_id的动作事件；最后在统一状态记录中提交变更，更新显示并记录异常日志。
3. **发布事件并保证event_id去重**：输入由唯一对象ID、世界层、当前世界时钟以及必要的物品/技能/位置构成；先验证目标、条件和容量，再发布带event_id的动作事件；最后在统一状态记录中提交变更，更新显示并记录异常日志。
4. **同步SharedWorldState**：输入由唯一对象ID、世界层、当前世界时钟以及必要的物品/技能/位置构成；先验证目标、条件和容量，再发布带event_id的动作事件；最后在统一状态记录中提交变更，更新显示并记录异常日志。
5. **可靠保存与版本迁移**：输入由唯一对象ID、世界层、当前世界时钟以及必要的物品/技能/位置构成；先验证目标、条件和容量，再发布带event_id的动作事件；最后在统一状态记录中提交变更，更新显示并记录异常日志。

## 3. 模块专属规则、数值逻辑与边界

### 统一空间、身份与时钟
世界位置用 `Vector3` 米坐标，X/Z为水平面、Y为高度；存档不可只用场景NodePath做身份。对象ID建议格式`world_seed/chunk_x/chunk_z/object_kind/local_serial`，重新进出区块保证同一个ID。实体拆分 `DefinitionId`（静态配方）+ `InstanceId`（唯一实例）+ `OwnerId`（容器、角色、世界或车辆）。`world_layer` 是实例所在层，不允许克隆一份真正的资产作为对照世界。

`SharedWorldState`保存门窗、矿脉、树木、家具、物资、墙体与发电网络；`LayerState[MAIN/INVERTED]`保存各层敌人、视觉气氛、层内陷阱和本层独立临时对象；玩家与载具实例只归属于一个当前层。事件结构含 `event_id/type/world_time/actor_id/target_id/payload/version`，同事件唯一结算。

跨线程：只能在线程内准备纯数据或引擎允许的离线资源，不在工作线程创建、增加或删除SceneTree节点。主线程每帧处理待提交队列。

## 4. 运行时数据与职责

- **定义资源**：`00_Definition`：保留静态属性、参数上下限、版本号和关联ID。
- **实例状态**：`00_InstanceState`：保留instance_id、world_layer、last_tick、state_version及本模块运行字段。
- **动作请求**：`00_ActionRequest`：actor_id、target_id、requested_time、payload、event_id。
- **写入策略**：本模块仅写其负责的实例字段，对其他模块通过事件和接口请求变更。

## 7. 操作失败与回滚

- 当资源不足、目标不可达、角色处于不允许动作的状态时，返回明确错误码，不消耗物品。
- 如果跨区块或跨世界转移时目标场景未准备好，延后提交并保持唯一旧实例。
- 读档重放已提交事件应跳过重复event_id；未提交事件恢复到可重试状态。

## 8. 模块级验收场景

- [ ] 同一事件重复投递100次只生效一次。
- [ ] 切换世界层后共享门窗与容器保持同一状态。
- [ ] 低内存、高速跨区、读档中断、异步资源未就绪和断电情形下行为有定义。
- [ ] 模块对外暴露的数据接口写成独立测试，不只依靠目视测试。

## 资源与接口要求
- 数据表使用UTF-8 CSV/JSON，字段包含ID、名称、数值、互斥与依赖；数值均为首轮测试值。
- 跨系统事件携带`event_id`以支持重复消息幂等处理；世界层共享状态不得重复实例化。
- 离线/卸载结算用绝对世界时钟；Node场景树增删应在主线程执行。
- 玩家移动与疾跑不因普通UI操作暂停；敌人照常感知玩家。

## 架构决策与全局契约
- 世界轴：Godot X/Z 水平，Y竖直；1 Godot单位 = 1米；平面图 1SVG米对应1游戏米；建筑楼层标高按 3.0—3.8 米配置。
- 静态定义与动态实例分离：`ItemDefinition`/`VehicleDefinition`/`BuildingDefinition` 可共享；`InstanceState` 单独保存，不得修改共享 Resource 写运行数据。
- 稳定标识：`world_seed:chunk_x:chunk_z:local_spawn_key` 生成基础实体ID；后建造物品使用 UUID；放入容器时转移所有权，不复制实例。
- 事件必须带 `event_id`、`world_tick`、`source_id`、`target_id`、`world_layer`，重复 event_id 不重复结算。
- 物品、车辆、建筑、矿脉和NPC任务是共享对象；丧尸与各层克苏鲁及当前天气表现是各自的层级运行实体。
- 统一操作：`TryUseItem`,`TryMoveItem`,`TryConsumeIngredients`,`ApplyDamage`,`SaveEntityDelta`,`RequestPath`,`CommitWorldTransfer`。
- 主线程只做场景树实例化与节点控制；后台可以生成纯数据和文件读取；`call_deferred` 将结果应用回主线程。

# 1. 项目定位与核心设计原则

## 1.1 游戏定位

制作一款以《僵尸毁灭工程》为生存探索参考、融合《逃离塔科夫》式空间背包、《七日杀》式身体伤害，以及克苏鲁宇宙恐怖元素的单人开放世界生存游戏。

武器模组的互动参考《ZERO Sievert》，家具/房屋用途参考《僵尸毁灭工程》，功能NPC和委托参考《泰拉瑞亚》与《七日杀》，简化电线连通参考《明日方舟：终末地》。本项目采用独立的游戏数值与实现，不直接复制其他作品的地图、角色、美术或具体数值。

玩家独自在大型地图中探索城镇、住宅、商业区、工业区、医院、军事设施和异常区域。玩家需要管理身体状态、食物、饮水、装备、弹药、伤势与精神状态，同时应对普通丧尸和具有特殊感知机制的克苏鲁生物。

## 1.2 核心设计支柱

  ------------------------------------------------------------------------------------
  设计支柱            目标
  ------------------- ----------------------------------------------------------------
  单人长期生存        玩家独立完成探索、决策、战斗与资源管理

  载具后勤与风险      驾驶提高远征效率，但消耗燃油、零件、道路和注意力

  有代价的搜刮        背包空间、重量、物品价值和撤离路线共同影响决策

# 17. 数据结构、存档与性能要求

## 17.1 技能数据

``` gdscript
class_name SkillData
extends Resource

@export var skill_id: String
@export var skill_name: String
@export var max_level: int = 25
@export var per_level_benefits: Array[Resource] = []  # 25条静态能力配置

# SkillProgress（独立运行态）存储base_level与current_xp；
```

``` gdscript
class_name BodyCondition
extends Resource

@export_range(-25, 25) var modifier: int = 0
@export var calorie_balance_bank: float = 0.0

func get_effective_strength(base_level: int) -> int:
    return base_level + modifier

    return base_level - modifier
```

正式项目中，体型变化的累计热量余额、基础技能等级和有效等级应分开保存。有效等级在读取时重新计算，避免存档数据不一致。

# 35. 核心规则与系统优先级

1.  **SAN规则：**
    SAN范围为0--100，数值越低代表精神状态越差；裂隙权重由SAN受损程度、异常关注度和区域污染共同决定。
2.  **异常关注度：**
    独立记录异常世界对玩家的关注程度，并控制高级遭遇阶段。
3.  **双世界数据：**
    两个世界共用建筑、物资和交互数据，环境与敌人生态按世界层切换。
4.  **敌人生态分层：**
    主世界运行丧尸生态，颠倒世界运行克苏鲁生态；跨界生物由专属能力和事件配置驱动。
5.  **克苏鲁感知：**
    视觉、特殊感知、光源和直接受击事件用于建立仇恨；普通声音事件由丧尸听觉系统处理。
6.  **仇恨追踪：**
    失去视线后，敌人使用最后发现位置、搜索范围和记忆时间更新目标。
7.  **速度与仇恨联动：**
    看见玩家时速度最高，失去视线后根据追踪和搜索状态减速。
8.  **固定型敌人：**
    主体锚定在指定位置，仇恨影响攻击频率、触手速度和攻击范围。
9.  **区域型敌人：** 按领地半径、巡逻点和追击边界管理活动范围。
10. **角色状态持续：**
    伤势、背包、食物消耗、技能、时间和SAN在世界切换后保持当前状态。
11. **返回路径：**
    每次进入颠倒世界时保存有效返回出口，并在出口变化时更新备用锚点。
12. **刷新管理：** 刷新由数量、距离、冷却、区域等级和环境预兆共同控制。

# 36. 项目执行规划与工作分解

# 39. 风险管理与技术验证清单

## 39.1 双世界同步风险

**验证重点：**
建筑、容器、门窗、家具和物品在两个世界使用相同实体ID和状态数据。

**技术措施：**
SharedWorldState集中管理实体状态；世界表现层根据当前WorldLayer读取状态；所有交互先更新共享数据，再刷新表现。

## 39.2 大地图AI性能

**验证重点：** 敌人数量增加时CPU、导航和物理开销的变化。

**技术措施：**
完整AI、简化AI和区域统计三级模拟；按玩家距离和区域活动状态切换更新频率。

## 39.3 建筑内部寻路

**验证重点：** 丧尸和克苏鲁能够识别门、楼梯、走廊和可破坏入口。

**技术措施：**
建筑内部导航区域分层管理，楼梯和门口使用连接点，破坏门窗后更新局部导航状态。

## 39.4 背包网格逻辑

**验证重点：** 物品旋转、堆叠、拆分、快速转移和容器嵌套后的占用正确性。

**技术措施：**
使用统一的GridContainer数据模型，UI只负责显示和操作请求，物品位置由InventorySystem验证和提交。

## 39.5 技能与体型计算

**验证重点：** 基础技能等级、有效技能等级和每一级能力解锁之间的关系。

**技术措施：**
基础等级永久保存；体型修正独立保存；有效等级实时计算；各级能力只读取基础等级。

## 39.6 克苏鲁追踪AI

**验证重点：** 视线中断、掩体、最后位置、搜索、仇恨衰减和区域边界。

**技术措施：**
将感知、仇恨、目标记忆、导航和攻击拆成独立组件；使用调试视线和目标点显示工具。

## 39.7 裂隙捕获与世界切换

**验证重点：**
抓取动画、玩家控制状态、目标世界落点、裂隙配对和存档恢复。

**技术措施：**
使用独立TransitionController管理过渡；切换前保存玩家状态和裂隙ID；切换后执行落点检测和状态恢复。

## 39.8 长期存档一致性

**验证重点：**
世界时间、热量余额、容器内容、敌人状态和裂隙状态的长期一致性。

**技术措施：**
存档使用版本号、唯一ID和时间戳；重要世界实体采用增量状态保存；读档后按依赖顺序恢复。

## 53.4 电网拓扑与负载结算伪代码

```gdscript
# 示意伪代码；实际按项目Resource与节点接口实现。
func recompute_grid_components() -> Array:
    var visited := {}
    var components := []
    for node_id in power_nodes.keys():
        if visited.has(node_id):
            continue
        var comp := bfs_valid_links(node_id, visited)
        components.append(comp)
    return components

func settle_component(component, delta_world_hours: float) -> void:
    var generation_kw := calculate_sources(component, weather_manager.current_state)
    var relay_kw := calculate_active_relay_usage(component)
    var available_kw := max(0.0, generation_kw - relay_kw)
    var storage := collect_storage(component)

    var consumers := get_consumers_by_priority(component)
    for consumer in consumers:
        if can_cover_load(available_kw, storage, consumer.power_kw, delta_world_hours):
            available_kw = serve_consumer(consumer, available_kw, storage, delta_world_hours)
        else:
            consumer.set_powered(false)

    charge_storage_with_surplus(storage, available_kw, delta_world_hours)
    settle_fuel_and_condition(component, delta_world_hours)
```

必须防止在环形连接中重复枚举电源；`can_cover_load()` 应考虑电池最大放电功率和剩余kWh，`charge_storage_with_surplus()` 应考虑最大充电功率、效率与容量。代码采用较长世界时间增量时，需要按光照/燃料变化分段结算。

## 53.5 感染结算伪代码

```gdscript
func apply_zombie_hit(attack_id: String, infection_amount: float, mitigation: float) -> void:
    if processed_attack_ids.has(attack_id):
        return
    processed_attack_ids[attack_id] = true
    var actual_gain := max(0.0, infection_amount * (1.0 - mitigation))
    infection_value = clampf(infection_value + actual_gain, 0.0, 100.0)
    refresh_infection_stage()

func update_infection(delta_world_hours: float) -> void:
    var growth := get_progression_rate(infection_value, active_treatments)
    var healing := get_treatment_rate(active_treatments)
    infection_value = clampf(infection_value + (growth - healing) * delta_world_hours, 0.0, 100.0)
    refresh_infection_stage()
```

攻击去重集合应按短期时间窗或持续攻击生命周期清理，避免无限增长；已发生的世界持久事件用事务ID防重复，普通战斗攻击ID不必永久保存在存档内。

## 53.6 武器属性重算伪代码

```gdscript
func rebuild_weapon_stats(weapon: WeaponInstance) -> Dictionary:
    var result := weapon_base_database[weapon.base_id].stats.duplicate(true)
    for slot_id in weapon.attachments.keys():
        var attachment_id = weapon.attachments[slot_id]
        var attachment_instance = inventory_system.get_item(attachment_id)
        var mod_data = attachment_database[attachment_instance.definition_id]
        apply_flat_and_percent_modifiers(result, mod_data)
    clamp_weapon_stats(result)
    return result
```

在正式实现中先汇总所有flat/percent项，再一次计算结果，以免配件顺序改变结果；模组更换时先校验背包空间、配件归属和兼容性，全部成功后才提交。

## 53.7 世界加载、AI与网络性能

天气可按气候区缓存，雨滴效果只在摄像机附近生成；电网仅在拓扑变化时重算连通分量，运行时按固定周期分配电力；远距离哨塔/NPC按时间切片进行概率战斗结算；室内检测用空间区域与上方遮挡，不对每个粒子逐点射线检测；建筑建造与拆除后局部标记导航区为dirty，批量刷新。角色感染、药物和电池运转采用世界时间戳而非UI帧时间。

## 53.8 一致性顺序

加载游戏时依次：静态定义数据库→世界时间/天气→共享建筑与容器→建造家具与电力节点/线路→玩家背包和武器实例→角色感染/技能→NPC及任务→电网拓扑恢复→世界层表现与敌人实例→UI与远距结算。先完整恢复电网，再让哨塔与工作台开始运行；先恢复任务物品唯一ID，再加载可交互容器，避免读档一帧内重复生成物资。

## 54.2 最小验证顺序

为了避免一次开发过多系统，建议先只做可验证的小闭环：一栋双层住宅、一条街、一场小雨、一名丧尸、一把可装瞄具的枪、一种基础抗生素、一棵可砍树、一块可开采的煤铁露头、一个小型熔炉、一个可摆放的柜子、一台燃油发电机、一台中继器、两盏灯、一个有弹药限制的自动哨塔、一名NPC、一台可驾驶轿车及一条修复供电委托。完成闭环后再加入太阳能、锂电池、燃烧式发电炉及异常裂隙。

## 54.3 系统完成定义（DoD）

每个系统至少满足：静态定义与运行态分离；可在测试地图实际操作；错误条件有明确提示；与玩家、敌人和世界时间完成关键联动；存档/读档正确；跨区流式加载不会复制状态；具备调试面板或可重复日志；对应验收场景通过；没有破坏原有克苏鲁视线追踪、SAN和双世界数据一致性。

## 54.4 AI编码任务切分

每次只向Codex/Gemini提交**一个明确工作包**，附前置接口与验收场景，减少一次性生成数十脚本的出错率。建议顺序：`InfectionSystem` → `WeatherManager` → `WeaponModificationSystem` → `ConstructionManager` → `PowerGridManager` → `TurretController` → `NPCPostManager` → `QuestManager` → 与 `SharedWorldState` 的最终整合。核心模块通过数据定义、信号和资源ID衔接，不允许新脚本私自实现另一个“时间管理器”“背包管理器”或“世界状态管理器”。

# 56. 存档兼容、数据归属与一致性规范

## 56.1 存档兼容原则

存档迁移应保留已存在的玩家状态、建筑容器、裂隙ID和物品实例，对缺失字段使用稳定的默认值，例如 `infection_value=0`、`electrical_skill.level=0` 与 `electrical_skill.xp=0`。武器以 `WeaponInstance` 方式读取，若发现不兼容的旧配件则放入安全恢复容器而非删除。天气按统一世界时间和世界种子初始化；无连接电网的消费者默认停机，不产生无限免费供电。载具还必须生成稳定 `vehicle_id` 并校验实际活跃世界层与货物唯一性。

## 56.2 存档格式与版本化

建议 `save_schema_version=6`，顶层包含：`player_state`、`body_injury_state`、`infection_state`、`skill_progress`、`inventory_instances`、`shared_world_entities`、`weather_regions`、`power_grids`、`npc_states`、`quest_states`、`world_layer_states`、`rift_pairs`、`vehicle_instances`、`vehicle_parts`、`vehicle_cargo_containers`、`vehicle_phase_transactions`、`resource_node_states`、`tree_instances`、`diggable_chunk_deltas`、`resource_transaction_ledger`、`processing_jobs`、`anomaly_state`、`timestamps`。迁移函数按版本逐级处理；先做原存档备份，迁移完成后检查唯一物品实例与网络连接合法性，再允许写回。

存档可采用一次写入临时文件、校验后原子替换的方式；每条关键事务分配唯一ID，避免断电/崩溃时部分成功导致物品复制。跨区离线模拟使用最后结算的世界时间戳，任务奖励、抗感染药物、太阳能发电、燃料/储电和NPC岗位不得在读档首帧再次完整结算。

## 56.3 全系统唯一数据归属

- 玩家七项状态：`PlayerStats` / `InfectionSystem`；没有第二份玩家感染变量。
- 旧有七部位局部伤势：`BodyDamageSystem`，局部伤口感染与丧尸感染严格分离。
- 技能等级与经验：`SkillSystem`；电力为十项技能之一，按逐级解锁统一管理。
- 背包、枪械和配件实例：`InventorySystem`；武器系统负责查询、计算和提交改装事务。
- 建筑、家具、容器、建造结构、树木、矿体/挖空区块、发电设备、电线及载具持久状态：`SharedWorldState`；载具仅在一个世界层运行可交互物理实例。
- 电网的运行算法：`PowerGridManager`；共享世界状态保存实际电能/燃料与网络连接。
- NPC的动态行为与岗位：`NPCManager`，默认属于主世界动态实体。
- 任务进度和领奖：`QuestManager`；不会直接复制建筑物资或重置全世界POI。
- 天气与时间：`WeatherManager` 引用 `WorldTimeManager`；不持有第二套独立世界时间。
- SAN和异常关注度：保持第11章分离；不与感染或NPC友好度混淆。
- 裂隙、颠倒世界与克苏鲁仇恨：遵守第21—34章独立组件；车捕裂隙由第81—84章进行权限检查及整车事务提交。

## 56.4 系统一致性检查清单

1. 在全部HUD、技能、状态、测试和存档中，将“六项”统一为“七项”、“九技能”统一为“十技能”。
2. 不更改第4章七个受击区域、第6章热量和体型算法或原有SAN含义。
3. 保留原有双世界建筑、家具、容器和物资共享规则，扩展到玩家建造、电网及其持久状态。
4. 保留丧尸声音感知与克苏鲁特殊感知差异；新增天气不能把两类敌人AI混为同一系统。
5. 感染100不是立即死亡；任何医疗系统都必须提供可持续降低感染值的游戏方法。
6. 发电源、太阳能、燃烧式发电炉与电池统一接入中继器网络；不新增第三种必需输电塔或复杂实际电路。
7. NPC以交易、任务和守卫为辅助；不替玩家自动完成长期冒险和异常研究。
8. 据点塔防消耗真实的弹药、燃料、电力和维修材料；远距离模拟不能无限产出奖励。
9. 所有系统均接入唯一ID、世界时间、区域流式加载、版本化存档和专用验收场景。
10. 载具的唯一物理实例、货物库存和乘员座位随R4/R5裂隙转层，不得双重刷车或跨层留下隐形乘员。
