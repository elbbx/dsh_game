# M23｜存档、事件台账、版本迁移与恢复——独立可执行设计书

> **定位：**本文件先给本模块的完整可执行设计与对应数据，再附106章原规划中属于本模块的条款。表中数值为初始游戏平衡配置，非已测试结论。

## 1. 玩家体验与系统边界

稳定ID、差量快照、双世界层实体、崩溃中途事务恢复。本模块不得绕过物品所有权、世界层身份、世界时钟和全局事件幂等机制。

## 2. 完整业务处理链

1. **定义存档schema和version**：输入由唯一对象ID、世界层、当前世界时钟以及必要的物品/技能/位置构成；先验证目标、条件和容量，再发布带event_id的动作事件；最后在统一状态记录中提交变更，更新显示并记录异常日志。
2. **写前事件去重并日志化**：输入由唯一对象ID、世界层、当前世界时钟以及必要的物品/技能/位置构成；先验证目标、条件和容量，再发布带event_id的动作事件；最后在统一状态记录中提交变更，更新显示并记录异常日志。
3. **定期原子快照+增量**：输入由唯一对象ID、世界层、当前世界时钟以及必要的物品/技能/位置构成；先验证目标、条件和容量，再发布带event_id的动作事件；最后在统一状态记录中提交变更，更新显示并记录异常日志。
4. **恢复后回放未完成事务**：输入由唯一对象ID、世界层、当前世界时钟以及必要的物品/技能/位置构成；先验证目标、条件和容量，再发布带event_id的动作事件；最后在统一状态记录中提交变更，更新显示并记录异常日志。
5. **清理悬空引用并生成校验报告**：输入由唯一对象ID、世界层、当前世界时钟以及必要的物品/技能/位置构成；先验证目标、条件和容量，再发布带event_id的动作事件；最后在统一状态记录中提交变更，更新显示并记录异常日志。

## 3. 模块专属规则、数值逻辑与边界

### 持久化事务
先把玩家属性、资源转移、容器变更、NPC任务奖励、移动建筑和裂隙转移等统一纳入EventLedger；每块保留静态seed和差异事件，不全量保存每株草。写入临时文件并`flush`后原子替换快照文件。存档版本升级要提供显式Migration脚本和旧版本回滚备份。保存时不能在主线程上一次写完几百MB。

## 4. 运行时数据与职责

- **定义资源**：`23_Definition`：保留静态属性、参数上下限、版本号和关联ID。
- **实例状态**：`23_InstanceState`：保留instance_id、world_layer、last_tick、state_version及本模块运行字段。
- **动作请求**：`23_ActionRequest`：actor_id、target_id、requested_time、payload、event_id。
- **写入策略**：本模块仅写其负责的实例字段，对其他模块通过事件和接口请求变更。

## 7. 操作失败与回滚

- 当资源不足、目标不可达、角色处于不允许动作的状态时，返回明确错误码，不消耗物品。
- 如果跨区块或跨世界转移时目标场景未准备好，延后提交并保持唯一旧实例。
- 读档重放已提交事件应跳过重复event_id；未提交事件恢复到可重试状态。

## 8. 模块级验收场景

- [ ] 中途断电不重复收获。
- [ ] 多模块共享实体无双份。
- [ ] 低内存、高速跨区、读档中断、异步资源未就绪和断电情形下行为有定义。
- [ ] 模块对外暴露的数据接口写成独立测试，不只依靠目视测试。

2. 列出该功能涉及的公共事件、ID、存档字段、输入与资源表；给出读写责任唯一归属。
3. 用可重复seed实现逻辑层，编写输入有效性与边界测试；不直接引入大量资产。
4. 接入Godot Node/UI/动画/物理，仅通过已批准接口调用其他模块。
5. 使用`07_验收与性能测试/`中的用例，在Demo测试场景完成人工流程。
6. 记录新增/修改文件、测试命令、实测结果、遗留风险和下一步切分，不合格不合并。

## 资源与接口要求
- 数据表使用UTF-8 CSV/JSON，字段包含ID、名称、数值、互斥与依赖；数值均为首轮测试值。
- 跨系统事件携带`event_id`以支持重复消息幂等处理；世界层共享状态不得重复实例化。
- 离线/卸载结算用绝对世界时钟；Node场景树增删应在主线程执行。
- 玩家移动与疾跑不因普通UI操作暂停；敌人照常感知玩家。

## 存档一致性
- Save header: schema_version, world_seed, world_time, active_layer, player_id, checksum；各chunk增量日志按entity_id+revision记录。
- 事件先追加 WAL 再更新内存对象，然后周期性做快照；同event_id重复回放无效。
- 容器转移为单写者事务：同时减少来源并增加目的地，失败不改变任何一侧；物品永久ID不可在两个容器同时存在。
- 载具转层须关联乘员和拖车，事务失败保证所有实体位于原层。跨层共享资源不能因两个世界同时更新而双倍推进。
- 离线时间按单个绝对世界时钟一次性结算；雨水、发电、制作、作物生长和疾病均使用last_simulated_tick防重复。

# 17. 数据结构、存档与性能要求

## 17.1 技能数据

建议使用独立 Resource 保存技能定义：

``` gdscript
class_name SkillData
extends Resource

@export var skill_id: String
@export var skill_name: String
@export var max_level: int = 25
@export var per_level_benefits: Array[Resource] = []  # 25条静态能力配置

# SkillProgress（独立运行态）存储base_level与current_xp；
# 不将每位玩家的进度写进共享的SkillData资源。
```

技能静态定义、技能当前等级经验、逐级能力与图纸/任务获得的配方知识应分开管理；逐级能力可依据基础等级重新计算。

## 17.2 食物数据

``` gdscript
class_name FoodData
extends Resource

@export var food_id: String
@export var food_name: String
@export var calories: float
@export var satiety: float
@export var weight: float
@export var inventory_size: Vector2i
```

## 17.3 体型数据

``` gdscript
class_name BodyCondition
extends Resource

@export_range(-25, 25) var modifier: int = 0
@export var calorie_balance_bank: float = 0.0

func get_effective_strength(base_level: int) -> int:
    return base_level + modifier

func get_effective_agility(base_level: int) -> int:
    return base_level - modifier
```

正式项目中，体型变化的累计热量余额、基础技能等级和有效等级应分开保存。有效等级在读取时重新计算，避免存档数据不一致。

## 17.4 敌人刷新架构

``` text
AnomalyManager
├── AnomalyAttention
├── HighestEncounterStage
├── SpawnPointDatabase
├── SpawnDirector
├── SpawnCooldown
├── ActiveCreatureLimit
└── RegionPollution
```

## 17.5 存档内容

至少保存：

-   玩家位置、朝向和世界时间。
-   七项生存状态。
-   身体部位伤势和疾病。
-   十种技能基础等级与经验。
-   逐级能力与配方永久解锁状态（由基础等级推导，并保留图纸/任务来源）。
-   当前背包、容器和装备。
-   物品耐久、弹匣和弹药状态。
-   当前热量累计余额。
-   当前体型修正。
-   SAN。
-   异常关注度。
-   最高遭遇阶段。
-   区域污染和世界事件状态。
-   已探索建筑和已搜刮容器状态。
-   据点设施和储物内容。

## 17.5A 存档字段定义
保存字段包括感染值与感染暴露记录、抗感染药物持续效果、电力技能经验、武器本体实例与全部配件实例、车辆/零件/油量/车内货物/座位与活跃世界层、车辆裂隙事件、天气种子/区域状态/预测时间、湿润状态、建造和家具实例与结构完整度、NPC身份/岗位/任务进度、发电机燃料和耐久、太阳能板状态、锂电池储电、各中继器和线缆连接的图ID、负载优先级和当前电网结算时间。共享场景物件不得按世界层各存两份。

## 17.6 大地图性能

地图敌人根据距离采用完整AI、简化AI和区域统计三级模拟。

建议三级模拟：

  距离     模拟方式
  -------- ----------------------------------
  近距离   完整AI、寻路、感知、攻击和动画
  中距离   简化移动和低频状态更新
  远距离   区域尸群数量、迁徙和简化事件模拟

建筑内部、楼层和外部空间的寻路连接需要统一管理，避免敌人进入建筑后无法正确上下楼。

# 23. 世界数据同步规则

## 23.1 必须同步的对象

以下对象在两个世界中共用同一份状态：

  对象         同步规则
  ------------ ------------------------------------
  地形与道路   坐标、地形结构完全一致
  建筑         外部结构、楼层、房间和碰撞结构一致
  门           开关状态、锁定状态、破坏状态一致
  窗户         完整、破碎、封堵状态一致
  家具         位置、旋转、移动和破坏状态一致
  容器         容器内容、已搜刮状态一致
  物资         是否存在、所在位置、数量一致
  车辆         数据/货物/耐久/燃油唯一；实际驾驶实体仅激活于active_world_layer，见第83章
  发电机       位置、燃油、开关和耐久状态一致
  玩家建造物   建造、升级和破坏状态一致
  地面物品     拾取、丢弃和移动状态一致

例如：

玩家在主世界打开某个住宅的后门，进入颠倒世界后，这扇后门仍然保持打开。

玩家在颠倒世界搜刮一个厨房抽屉，返回主世界后，这个抽屉也必须保持已搜刮状态。

玩家在颠倒世界打碎一扇窗户，主世界对应位置的窗户也必须是破碎状态。

## 23.2 物资防重复规则

物资必须拥有全局唯一的实体 ID。

例如：

``` text
container_id: house_014_kitchen_drawer_02
item_instance_id: item_00008342
```

同一容器使用全局唯一ID和共享物资列表，两个世界读取同一份容器状态。

正确逻辑：

1.  地图初始化时，根据固定种子生成容器物资。
2.  生成结果写入共享世界状态。
3.  两个世界显示同一份容器数据。
4.  玩家在任意世界拾取物品，物品从共享世界状态中移除。
5.  切换世界后，另一个世界对应位置读取更新后的共享状态，保持物品已拾取结果。

## 23.3 玩家背包同步

玩家背包是全局唯一数据：

-   玩家在颠倒世界拾取的物资，返回主世界后仍然在背包中。
-   玩家在颠倒世界消耗的弹药记录在全局背包数据中，返回后保持消耗结果。
-   玩家在颠倒世界受到的伤害会保留。
-   玩家在颠倒世界消耗的食物、水和医疗用品记录在全局物品状态中，返回后保持当前数量。
-   玩家在颠倒世界产生的体力、疲劳和SAN变化会保留。

玩家背包和角色数据由全局PlayerState统一管理，世界切换只更新所在世界层和坐标。

## 23.4 敌人数据不同步

敌人属于世界层专属实体：

  敌人           主世界               颠倒世界
  -------------- -------------------- ------------------------------
  普通丧尸       主世界丧尸生态       颠倒世界使用独立克苏鲁生态层
  特殊丧尸       主世界特殊丧尸       颠倒世界使用独立克苏鲁生态层
  T1观察者       可以按区域规则出现   可以出现
  T2异常潜伏体   可以出现             可以出现
  T3狩猎者       可以出现             可以出现
  T4高级猎食者   高污染区域出现       可以出现，权重更高
  T5领域守护者   固定事件或特殊区域   固定事件或特殊区域

主世界丧尸保留独立世界层状态；玩家进入颠倒世界期间，丧尸使用区域简化模拟，玩家返回后恢复对应活动状态。

两个世界按世界层管理敌人生态；跨越裂隙的特殊生物通过专属能力和事件配置实现。

## 23.5 时间同步

两个世界使用同一套世界时间。

玩家在颠倒世界停留期间：

-   世界时间继续流逝。
-   玩家饥饿、口渴、疲劳和卡路里收支继续计算。
-   主世界丧尸可以使用低频模拟更新。
-   主世界容器和建筑沿用共享实体状态，保留已搜索、破坏和交互结果。
-   颠倒世界敌人继续按照其世界层规则活动。

世界时间和玩家生存状态在世界切换期间持续推进，远距离区域事件使用低频模拟。

# 56. 存档兼容、数据归属与一致性规范

## 56.1 存档兼容原则

存档迁移应保留已存在的玩家状态、建筑容器、裂隙ID和物品实例，对缺失字段使用稳定的默认值，例如 `infection_value=0`、`electrical_skill.level=0` 与 `electrical_skill.xp=0`。武器以 `WeaponInstance` 方式读取，若发现不兼容的旧配件则放入安全恢复容器而非删除。天气按统一世界时间和世界种子初始化；无连接电网的消费者默认停机，不产生无限免费供电。载具还必须生成稳定 `vehicle_id` 并校验实际活跃世界层与货物唯一性。

## 56.2 存档格式与版本化

建议 `save_schema_version=6`，顶层包含：`player_state`、`body_injury_state`、`infection_state`、`skill_progress`、`inventory_instances`、`shared_world_entities`、`weather_regions`、`power_grids`、`npc_states`、`quest_states`、`world_layer_states`、`rift_pairs`、`vehicle_instances`、`vehicle_parts`、`vehicle_cargo_containers`、`vehicle_phase_transactions`、`resource_node_states`、`tree_instances`、`diggable_chunk_deltas`、`resource_transaction_ledger`、`processing_jobs`、`anomaly_state`、`timestamps`。迁移函数按版本逐级处理；先做原存档备份，迁移完成后检查唯一物品实例与网络连接合法性，再允许写回。

存档可采用一次写入临时文件、校验后原子替换的方式；每条关键事务分配唯一ID，避免断电/崩溃时部分成功导致物品复制。跨区离线模拟使用最后结算的世界时间戳，任务奖励、抗感染药物、太阳能发电、燃料/储电和NPC岗位不得在读档首帧再次完整结算。

## 56.3 全系统唯一数据归属

- 玩家七项状态：`PlayerStats` / `InfectionSystem`；没有第二份玩家感染变量。
- 旧有七部位局部伤势：`BodyDamageSystem`，局部伤口感染与丧尸感染严格分离。
- 技能等级与经验：`SkillSystem`；电力为十项技能之一，按逐级解锁统一管理。
- 背包、枪械和配件实例：`InventorySystem`；武器系统负责查询、计算和提交改装事务。
- 建筑、家具、容器、建造结构、树木、矿体/挖空区块、发电设备、电线及载具持久状态：`SharedWorldState`；载具仅在一个世界层运行可交互物理实例。
- 电网的运行算法：`PowerGridManager`；共享世界状态保存实际电能/燃料与网络连接。
- NPC的动态行为与岗位：`NPCManager`，默认属于主世界动态实体。
- 任务进度和领奖：`QuestManager`；不会直接复制建筑物资或重置全世界POI。
- 天气与时间：`WeatherManager` 引用 `WorldTimeManager`；不持有第二套独立世界时间。
- SAN和异常关注度：保持第11章分离；不与感染或NPC友好度混淆。
- 裂隙、颠倒世界与克苏鲁仇恨：遵守第21—34章独立组件；车捕裂隙由第81—84章进行权限检查及整车事务提交。

## 56.4 系统一致性检查清单

1. 在全部HUD、技能、状态、测试和存档中，将“六项”统一为“七项”、“九技能”统一为“十技能”。
2. 不更改第4章七个受击区域、第6章热量和体型算法或原有SAN含义。
3. 保留原有双世界建筑、家具、容器和物资共享规则，扩展到玩家建造、电网及其持久状态。
4. 保留丧尸声音感知与克苏鲁特殊感知差异；新增天气不能把两类敌人AI混为同一系统。
5. 感染100不是立即死亡；任何医疗系统都必须提供可持续降低感染值的游戏方法。
6. 发电源、太阳能、燃烧式发电炉与电池统一接入中继器网络；不新增第三种必需输电塔或复杂实际电路。
7. NPC以交易、任务和守卫为辅助；不替玩家自动完成长期冒险和异常研究。
8. 据点塔防消耗真实的弹药、燃料、电力和维修材料；远距离模拟不能无限产出奖励。
9. 所有系统均接入唯一ID、世界时间、区域流式加载、版本化存档和专用验收场景。
10. 载具的唯一物理实例、货物库存和乘员座位随R4/R5裂隙转层，不得双重刷车或跨层留下隐形乘员。

# 83. 车辆跨世界状态、乘员、拖车、返程与防软锁

## 83.1 共享状态与独立活跃层

为了同时满足第22—23章的**世界实体共用唯一状态**和“车辆确实被吞入颠倒世界”，车辆采用 `VehicleInstance` 唯一数据、`active_world_layer` 单一实际层、`world_position` 单一物理坐标。切换世界改变的是车辆实际参与物理碰撞、交互和AI感知的世界层；车辆在另一世界可显示非交互的“异常映像”，但**不能复制可驾驶车辆**。建筑、路面、门窗与家具仍保持原有跨世界完全共享；车辆是其中具有活跃层归属的移动实体。

| 车辆数据 | 跨世界规则 |
|---|---|
| `vehicle_id`、车型、外观改装 | 唯一、跨世界保留 |
| 坐标、朝向、速度 | 同一持久状态；相位转移时执行安全位置映射 |
| 发动机、油量、油路、油箱破损 | 唯一，不因穿越满油/归零 |
| 电瓶电量、零件健康、轮胎状态 | 唯一，世界切换继续耗电/损坏规则 |
| 后备箱、货斗、乘客背包 | 全局唯一库存和实例ID |
| 车门、车窗、车灯和警报器 | 唯一功能状态，环境表现可以覆层 |
| 乘员与座位预约 | 由同一个车辆转移事务处理，不复制NPC |
| 牵引关系、拖车库存 | 独立ID、可根据裂隙容量一起转移或断开 |
| 实际物理/交互层 | 只能是 `MAIN_WORLD` 或 `INVERTED_WORLD` 之一 |

## 83.2 乘员的世界层规则

玩家始终以当前座位为根对象，与整车在同一个事务切换层；玩家七项生存状态、SAN、感染、伤势、药物计时不暂停。**NPC默认不在颠倒世界自然生成或驻扎**，但**已实际乘坐该车并被同一次裂隙事件捕获的NPC**可以作为临时同行者被带入：原NPC实例从主世界动态实体池移至车辆乘员名单，进入颠倒世界后用低复杂度“留车/跟随玩家撤离/有限自卫/恐惧”行为；离开车辆时在目标层创建同一个NPC的活动节点，主世界不保留其可交互复制体。返回主世界后恢复岗位/任务关系；若同行NPC死亡，唯一身份记录持久保存。

这项同行许可是“被车一起拉入”的物理事件例外，不会让颠倒世界出现随机居民NPC、任务商人或据点守卫分身。

## 83.3 拖车和牵引组如何通过

- 裂隙需对主车和拖车**整组质量、总外形包络、连杆角度**进行认证。
- 满足R5的群体捕获规则时，主车、拖车及各自独立库存作为一个事务转移，挂接关系保留。
- 主车可通过但拖车不符合容量时，先播放挂钩受力警告；允许玩家在安全窗口解除挂接。若继续捕获，按事件配置断开挂钩：主车被吞、拖车留在原层，彼此 `tow_link_id` 清除；拖车与其货物仍是唯一实体。
- 禁止先把车切世界再逐帧拉拖车通过裂隙造成两层刚体互相牵引。分层刚体之间不能保持物理关节。

## 83.4 颠倒世界驾驶和环境

颠倒世界沿用相同道路、高度和碰撞布局，因此普通路面可以驾驶，但异常光照、腐化覆层与敌人生态改变体验。颠倒世界不刷新丧尸，只刷新克苏鲁；车灯可能激活部分T3/T4光感知，发动机普通噪声不令克苏鲁拥有原本不存在的听觉，但车辆的**存在、移动、直接碰撞、特殊异常感应**仍可使其锁定。高污染地点可增加局部异常阻滞或车窗视觉干扰；此效果必须明示，不可直接瞬间摧毁发动机。

若玩家在颠倒世界停下并离车，车辆保留在颠倒世界，位置和货物持久保存；玩家可以走远、通过普通人物裂隙返回，但不能要求已留在颠倒世界的车也无条件回主世界。若另一个世界显示车辆残影，该残影不可装货、开车、维修或被NPC拖走。

## 83.5 返回主世界

- 徒步返回继续使用第26章的**至少一个可达出口**保底；这个保底只对人物生存有效，不等于任意裂隙可供汽车通过。
- 开车返回必须找到 `vehicle_passage_allowed=true`、质量/尺寸匹配、可接近且当前有效的裂隙；稳定高等级裂隙和特殊大型通道优先作为载具回程路线。
- 车辆经过返程裂隙时走与进入一致的授权、动画与原子转移流程，保留全部物品、油量、车损和乘员。
- 地图与日志标记“人物可通过”“载具可通过”“本车体积/质量不适用”和已知通道方向，帮助玩家规划携车撤离。
- 如果玩家把车遗弃在颠倒世界，允许在任务中获取车辆回收信息并前往有效回程裂隙；不免费把车送回据点。玩家死亡或存档重载时同样保留车的位置与活跃世界层。

## 83.6 极端情况和保底

1. 目标锚点的共享建筑或地形被改造到不允许停车：从附近候选可驶入表面寻找整车合法落点并保留朝向，不能只检查玩家脚下2m的普通安全点。
2. 目标点在桥梁边、车库、车顶或水面：执行多点地面/坡度/上方空间检测；不满足则拒绝相位转移，触手释放并进入冷却。
3. 驾驶途中被捕获但玩家突然存档：记录 `pending_transfer_id` 与阶段；读档后要么完成整车转移，要么回滚到上一个合法驾驶位置，不能车和角色分离。
4. 车辆中途爆炸或毁坏：停止相位过程，结算残骸、货物和乘员，各实体归属清晰；不可生成两具车壳。
5. 车内NPC因任务变化被移除：先释放真实座位占用，再更改任务状态，不能保留隐形NPC碰撞体。
6. 车辆与拖车跨区装载：相关两个区块在事务提交前短时固定加载；成功后异步卸载旧层，不通过全世界扫描找实例。
7. 玩家成功徒步离开颠倒世界，而车辆仍在其中：可以在角色界面查阅最后已知车辆位置；人物不会被强制困住。
8. 相位转移时远距离据点电网与NPC继续按世界时间单次结算，不因为车辆进入新层重新生成据点物资。

# 96. 颠倒世界矿产树木与世界同步

## 96.1 共享数据原则

主世界与颠倒世界地图坐标、房屋结构、可砍树木、地表石块、矿体储量、矿道挖空、支柱、物资容器和玩家建造结构使用同一份权威数据。主世界砍倒一棵树后，颠倒世界对应树不再是另一棵可独立采伐的完整树；颠倒世界挖掉一格煤矿后，主世界对应矿格也被挖空。

环境表现可以不同：颠倒世界树木呈异常颜色或被附着菌丝，岩壁有异常纹理，矿坑存在特殊光照与克苏鲁生态；这些视觉差异默认不改变共享木料与矿产数量。剧情专属异常矿晶可作为独立世界层事件资源，但必须拥有唯一ID、明确掉落与生成规则，不干扰普通矿物共享储量。

## 96.2 物资掉落与互斥

矿物开采掉落采用 `harvest_transaction_id` 原子写入：先从共享矿块扣除储量，再生成一份可交互资源实例，绑定唯一物品ID和当前实际物品容器/地面位置，提交后在两个世界渲染共享的对应物品视图。任何时候同一地面物品只能被拾取一次。树木倒伏时也只生成一次木料；如果玩家在转层前未拾取矿物，其物品数据仍然保持共享归属，不出现平行世界重复掉落。

## 96.3 地形空腔和空间传送

两个世界共用同一个矿洞空腔与支护数据；玩家在矿坑中进入裂隙后，目标层的安全落点必须检查当前已经挖空的实际空间、坡度、可站立面及克苏鲁碰撞。矿洞内可配置行人裂隙，但必须有至少一条安全返回路径。车辆仍仅由第81—84章R4/R5可抓车裂隙单独转层；共享矿坑不能直接变成任意车辆的无条件世界传送门。

## 96.4 矿坑生态分层

主世界地下可出现丧尸及少量符合区域规则的克苏鲁，颠倒世界矿洞内只刷新克苏鲁；NPC主要属于主世界的动态实体。地下开采声音由普通丧尸听觉处理；颠倒世界克苏鲁仍遵守视觉、光源和异常感知，不因为共享声音事件而得到普通听觉能力。

## 96.5 防卡死与恢复

如果地形编辑、局部塌方、跨层传送或读档导致角色站在实心矿格内，使用已保存的安全锚点与局部空间投射将角色放到附近合法位置；不能以此复制矿石、免费生成出口或重置地形。若载具在矿区附近跨层，应保持车辆尺寸/落点验证与车货唯一性。游戏存档仅需保留一次矿洞差量数据、一次树木状态与唯一资源事件记录。

# 105. Godot接口、存档字段、事件与状态机

## 105.1 推荐组件职责

```text
Player
├── PlayerMovement            # WASD/Shift始终根据角色状态更新

├── EquipmentSystem           # 三个通用武器槽、衣物及专用设备槽
├── InventorySystem           # 唯一物品实例、网格容器与事务

HUD (CanvasLayer)
├── CoreStatusRings           # 六个常驻状态，图标在圆心
├── DynamicStaminaRing        # 角色3D投影位置附近动态体力环
├── TemporaryStatusRings      # 体温、疾病、伤势等临时圆环
├── QuickCategoryBar          # 六个永久分类槽，不储存物品
```

| `StaminaRingState` | `last_consumption_at`、`fade_progress` | 1秒滞留与淡出 |
| `MedicalActionState` | `action_id`、`item_instance_id`、`target_part`、`started_at`、`committed` | 防重复医疗结算 |

需要长期存档的字段：实际库存、装备槽实例ID、药物效果和角色状态；可选保存最近选择的类别和道具定义。**轮盘剩余超时、鼠标位置、屏幕右侧体力环动画进度属于瞬态UI**，不应写入跨世界的永久世界实体存档。读档后必须重新从Inventory/Equipment生成候选，不信任旧UI缓存。

## 105.3 统一行为伪代码

```gdscript
# 示意：不依赖具体项目脚本路径
func select_quick_category(category_id: int) -> void:
    var candidates = quick_access_resolver.resolve(category_id)
    if candidates.is_empty():
        hud.show_empty_category_feedback(category_id)
        return
    if candidates.size() == 1:
        hand_item_controller.request_equip(candidates[0].item_instance_id)
        return
    ui_state_coordinator.open_radial(category_id, candidates, 5.0)

func on_top_item_clicked(item_id: StringName) -> void:
    # 查询最新实时权限，避免列表打开期间物品被转移/用完
    if not quick_access_resolver.is_still_accessible(item_id):
        return
    var item = inventory_system.get_instance(item_id)
    if item.category in [&"FOOD", &"DRINK", &"GLOBAL_MEDICINE", &"LOCAL_MEDICAL"]:
        item_action_router.request_use(item_id)
    else:
        hand_item_controller.request_equip(item_id)
    ui_state_coordinator.close_top_panel()
```

对`1/2`多件武器，`resolve`返回武器实例序列；对`3—6`返回可用的物品类型/分组视图，实际选中后仍必须解析到真实实例ID。上述伪代码中的`candidates.size()`对应最终有效候选数，实施时需按“武器实例计数、消耗品按类型合并”规则预处理，不能简单统计物品堆叠数量。

## 105.4 Godot输入与进程控制

`PlayerMovement`持续读取`Input.get_vector()`和疾跑动作；`UIInputRouter`只管理鼠标归属，优先使用专门的输入入口确保`Control.accept_event()`不会意外吞掉移动指令。`CanvasLayer`与角色/AI/世界均正常处理；UI计时应采用真实时间或自带process计时，而不是通过暂停的世界时钟。若项目允许全局时间倍率变化，应明确统一使用哪种时钟，确保UI“5秒”始终代表约5秒真实时间，而非随世界倍率加速。

物品转移使用`InventoryTransaction`的“检查目标格→验证物品位置→变更→发信号→刷新候选”原子流程。动作完成时提交医疗耗材或食物消耗，已完成操作必须有事务ID；UI切换、世界切换、读档与角色死亡时不得重复提交同一笔操作。`InventoryChanged`、`EquipmentChanged`、`ItemConsumed`、`StaminaConsumed`、`TemporaryStatusChanged`分别驱动对应UI刷新，不需要每帧扫描所有物品。
